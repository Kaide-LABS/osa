OSA — One-Shot Anything

One prompt in, a researched, specified, built and checked project out. OSA drives the AI coding tools you already have signed in, and leaves evidence at every step: a hash-locked plan, mandatory documentation, a reviewer that is a different model from the author, and a final check that runs the project.

Install

npm install -g @kaide-labs/osa
osa setup          # register OSA's MCP server with Claude Code
osa mcp-config     # or print the entry for Cursor, VS Code, Windsurf, Claude Desktop, ...

Then, in any git repository: osa "build me a command-line word counter", or ask your assistant to use OSA. OSA has no model or API key of its own: it drives Claude Code, Codex CLI, OpenCode, Antigravity or GitHub Copilot CLI. One is enough.

How it works

  1. Intake. A plain-language plan: TL;DR, scope, testable acceptance criteria, and every assumption tagged risky, defaulted or safe. A broad request gets up to 3 suggested questions with default answers. Answering is optional but recommended.Nothing is assumed silently.
  2. Automatic lock. The plan is hashed (SHA-256) and committed.Any later change to it is a hard failure.
  3. Research. Official documentation for every library named, academic papers (arXiv, OpenAlex), GitHub prior art; then a second model checks the report's claims.A spec with no documentation source fails.
  4. Spec. Phase specs; gaps become logged decisions, never questions.Every decision made for you is on record.
  5. Agents. A lateral-architecture agent proposes a different design; an implication agent adds second-order acceptance criteria.The architecture choice and its reason are recorded.
  6. The one confirmation. A TL;DR built from the spec, its decisions, what research could not confirm, and the risky assumptions, assembled without another model call and tied to a hash of the spec. You approve once.The spec you approve is the spec that gets built.
  7. Build. Per phase: two executor turns and a reviewer turn, verified through git, file hashes and continuity checks.The reviewer is a different seat from the author.
  8. Application check. An agent runs the finished project in a disposable copy and tries each acceptance criterion; it has no file-edit tool.No pass without a command and its observed output.
  9. Summary and memory. A plain-language summary (what was built, decided, uncertain, and how it was checked), and facts saved for the next run.Secrets are rejected; memory comes from the run record, not model prose.

Over MCP: four tools

ToolWhat it does
osa_planWrites the plan and its fingerprint. Builds nothing. Returns any recommended questions for a broad request.
osa_specLocks the plan automatically and runs research and the spec in the background, then waits.
osa_statusProgress; when the spec is ready, awaiting_confirmation with the TL;DR, a spec hash and the risky assumptions.
osa_buildThe one confirmation. Refuses a hash that is not the spec you saw, a spec file changed afterwards, or risky assumptions nobody accepted.

Unattended on the command line: --yes builds only when nothing is risky; --yes --accept-risky is fully hands-off and records every risky and defaulted item. New in v0.5.0.

Review independence, measured by model

A seat is a provider and a model

The bias a review is meant to remove belongs to the model, not the vendor's tool. So one subscription is enough: a cheaper model writes, a stronger one reviews.

Reported, never refused

Six levels, strongest first: different model family, different capability class, different provider, different model, unverified, same model. OSA picks the strongest arrangement available and says plainly which one it got.

Other numbers

  • The independent research checker caught 13 of 15 planted false facts with 0 false alarms (a small planted-fact test).
  • A spec-only run on a library prompt: about 22 minutes and 27 model calls (research about 14 minutes, spec about 6).
  • The test suite at v0.5.0: 1,243 of 1,257 pass, 0 fail; 14 are skipped live tests that need real provider tools. An automated architecture-boundary scan finds 0 violations in 148 files.
  • Dependencies: two (zod and the MCP SDK).

Built with itself

OSA's own one-confirmation gate (v0.5.0) was planned, researched and specified by OSA. The build ran with Claude Haiku, the smallest and cheapest Claude model, writing the code and Claude Opus reviewing. Haiku wrote most of the change. The run also crashed three times and left real bugs, a lock that refused too eagerly and a gate that never cleared, which the checking caught and which were fixed by hand. That is the design working as intended: a cheap model writes, a different model checks, and nothing ships on the writer's word.

Found by running it for real

  • arXiv returned no papers for long queries because it requires every word to match. A query that finds nothing is now retried with fewer words.
  • A provider that exited before reading its prompt took the whole harness down. It is now one failed call.
  • Codex on Windows wrote a byte-order mark that broke a valid record. OpenCode's headless web search never worked, so OSA does not claim it.
  • GitHub search returned nothing for long queries; a stopped run's summary leaked engineering text; the repository's own config file was invalid JSON, caught by the new doctor report.

Honest limits

  • Recorded end-to-end runs were on a Claude Code and Codex pair; a full build on the newest release with one provider has not yet been documented.
  • The Copilot adapter is experimental and untested against the real tool; Antigravity's text calls were slow and unreliable in our runs.
  • Prompt-injection screening of web text reduces the risk; it does not eliminate it.
  • Visual checks of user interfaces are not done; the strongest fit today is command-line tools, libraries and APIs.
