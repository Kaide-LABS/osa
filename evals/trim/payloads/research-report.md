This build targets Node.js, whose standard library fully covers every acceptance criterion without any npm packages. Use `node:fs` (`readFileSync` with `'utf8'` encoding) to read each file, `process.argv` (slicing off the first two elements) to get the file paths, `try/catch` around each read for resilient per-file error handling, and `process.exitCode = 1` to signal a nonzero exit while still finishing all output. As of October 2026 the Active LTS line is Node.js 24.x (recommended for this CLI) and the Current line is Node.js 26.x; both ship these APIs unchanged.

**Key findings**

**Recommendations**
- Read each file with fs.readFileSync(path, 'utf8') inside a per-file try/catch so one ENOENT (missing file) does not abort the rest of the loop.
- Derive the file list from process.argv.slice(2); print one `<filename>: <count>` line per file and a final total line summing only successfully-read files.
- Count words by trimming then splitting on /\s+/ and filtering out empty strings, so leading/trailing whitespace and multiple spaces don't inflate the count.
- On a failed read, write the error (identifying the file) to stderr and set `process.exitCode = 1`; do NOT call process.exit(1) immediately — setting exitCode lets valid files still print and avoids truncated output.

### Reading files and CLI arguments with the Node standard library
*How to read process arguments, read file contents, and distinguish a missing-file error (ENOENT) from other read errors using only built-in modules*

Use only the `node:process` and `node:fs` built-in modules. Read user-supplied file paths from `process.argv`, where index 0 is the Node executable, index 1 is the script path, and index 2 onward are the user arguments — so slice from index 2. Read each file synchronously with `fs.readFileSync(path, 'utf8')` (or async `fs.readFile`/`fs.promises.readFile` with the `'utf8'` encoding) to get a string, wrapping the read in try/catch. To distinguish a missing file from other failures, inspect the caught error's `err.code` property: it equals `'ENOENT'` for a nonexistent file (vs e.g. `'EACCES'` for permission denied); never match on `err.message`, which is unstable across versions. The error object also carries `err.path`, which names the offending file for the per-file error message.

**Key findings**
- `process.argv` is an array: index 0 = `process.execPath` (Node binary), index 1 = absolute path of the running script, indices 2+ = user-passed arguments; so user files are `process.argv.slice(2)` (Node.js v26.12.0 docs).
- `fs.readFileSync(path[, options])` returns a string when an encoding such as `'utf8'` is passed, otherwise a `Buffer` (Node.js v26.12.0 docs).
- A missing path causes the read to fail with a system error whose `code` property is `'ENOENT'` ("Error NO ENTry"); check `err.code === 'ENOENT'` to detect it specifically (Node.js v26.12.0 docs).
- Node.js system errors expose `error.code`, `error.syscall`, `error.path`, `error.errno`; `error.path` holds the file path involved, useful for identifying which file failed (Node.js v26.12.0 docs).
- Docs explicitly warn: `error.message` may change in any version — use `error.code` for stable error identification (Node.js v26.12.0 docs).
- `fs.readFile(path[, options], callback)` delivers errors as the callback's first argument; `fsPromises.readFile(path[, options])` rejects the promise; both accept `'utf8'` to return a string (Node.js v26.12.0 docs).
- Setting `process.exitCode = 1` marks a nonzero exit while letting the event loop drain and pending stdout writes complete; `process.exit(1)` forces immediate termination and can truncate stdout output (Node.js v26.12.0 docs).

**Recommendations**
- Read file arguments with `process.argv.slice(2)`; if it's empty, you may print usage and set a nonzero exit code.
- Use the synchronous `fs.readFileSync(file, 'utf8')` inside a per-file try/catch for the simplest resilient loop — one file's failure does not stop the others; async `fs.promises.readFile` with Promise.allSettled is an alternative if concurrency is wanted.
- In the catch block, branch on `err.code`: treat `'ENOENT'` as a missing-file error and print a message naming the file (use `err.path` or the original argument); let other codes surface as generic read errors. Do NOT parse `err.message`.
- Avoid pre-checking existence with `fs.existsSync` then reading (a TOCTOU race); instead attempt the read and catch `ENOENT` — fewer syscalls and no race window.
- Set `process.exitCode = 1` (not `process.exit(1)`) when any file fails, so the valid files' counts and the total are fully printed before the process exits with a nonzero status — satisfying acceptance criteria 5 and 7.
- Import only `node:fs` and `node:process` (both built-in); keep package.json `dependencies` empty to satisfy criterion 6.

### Per-file error handling and process exit codes in Node CLIs
*How to continue processing remaining files after one fails and set an appropriate exit code to signal partial failure*

For this word-counting CLI, read each file inside a try/catch (or per-file callback) so that a failure on one file never aborts the loop over the remaining files. On an error (e.g., a missing file), print an identifying error message to stderr, set `process.exitCode = 1` rather than calling `process.exit(1)`, and continue to the next file. Because `process.exitCode` only takes effect when the event loop drains, all valid files still get counted and the per-file lines plus the grand total are printed, while the nonzero code still signals partial failure. Prefer `process.exitCode` over `process.exit()` so buffered stdout/stderr output is reliably flushed before exit.

**Key findings**
- `process.exitCode` lets you set the eventual exit code while allowing the process to exit gracefully; its type is integer|string|null|undefined, default `undefined`, added in Node v0.11.8 (per nodejs.org process docs).
- `process.exit([code])` immediately terminates the process (default code 0, added v0.1.13); as of Node v20.0.0 it only accepts numbers or integer strings.
- Node's official docs explicitly recommend setting `process.exitCode = 1` and letting the process exit naturally instead of calling `process.exit()`, so pending I/O completes, 'exit' listeners run, and stdout/stderr buffers are flushed.
- `process.exit()` can truncate or drop output because console/stdout writes may be asynchronous depending on the connected stream (TTY vs pipe/file); piped or CI-captured output is most at risk (echooff.dev, published 2026-06-04, updated 2026-09-06).
- Exit-code convention is standard on Unix-like systems: 0 = success, any non-zero = error; a single nonzero code (commonly 1) is sufficient to signal that at least one file failed.
- The documented per-file pattern is: on read error, `console.error(...)` + `process.exitCode = 1` + `return`/continue, so the loop proceeds to the next file.

**Recommendations**
- Wrap each file read in its own error boundary (try/catch around a synchronous `fs.readFileSync`, or per-file error handling in the async callback/promise) so one failure does not stop the others.
- On any per-file failure, write a message identifying the specific file to stderr (`console.error`) and set `process.exitCode = 1`; then continue the loop — do not throw out of the loop.
- Set `process.exitCode = 1` for partial failure rather than calling `process.exit(1)`; `process.exit()` can terminate before the per-file counts and the total have been flushed to stdout, which would violate the requirement that valid files still print.
- Print all per-file count lines and the computed total before the process exits naturally; since `exitCode` does not force immediate termination, the total still prints while the nonzero code is preserved.
- Use a single nonzero code (1) for 'at least one file failed'; avoid over-engineering distinct codes — the acceptance criteria only require nonzero-on-missing-file while valid files are still processed.
- Avoid letting an unhandled exception from one bad file propagate (which would set a nonzero code but skip remaining files and the total) — catch it locally.
